# Programme reference maxes

A definition may declare `maxBasis: "1rm" | "tm" | "e1rm"`. This is source metadata, not a request to scale the entered max. Percentages multiply that reference directly. Authors must verify the source basis before setting the field. The UI labels unspecified definitions as “Reference max (basis unspecified)”. Recognized unanimous legacy `tm.reference` values can supply the basis; `lb` and `as-authored` cannot. Legacy definitions remain readable without modification.

`setTrainingMax(state, cycleId, {lift, value, unit, today, reason?, now?}, index?)` mutates a caller-owned draft for an active/paused cycle. `lift` is the stable source lift/variant key declared in `tmSeeds` or slot `tm.key`, or an existing cycle max key. Values must be numeric, positive and finite; units must be explicit `lb` or `kg`. The event records the calendar effective date and a monotonically increasing millisecond recording clock. Backdated appends are refused. UI writes retain the captured account, profile, document generation, session identity and cycle revision through the store producer. Transport callers remain responsible for authentication and conditional persistence.

Each append adds `cycle.maxAdjustments[] = {id, lift, recordedAt, effectiveOn, previous, value, unit, basis?, reason}`. Values and previous values are normalized once, without load rounding, into the frozen definition's unit; the event's `unit` makes that explicit. Profile-unit changes convert the display cache but leave events, original `tmSeed`, frozen definition and completed logs unchanged. Unknown extension data survives edits and merging. The merge unions event identities, sorting by effective date, recording clock and id; distinct concurrent appends survive. Concurrent same-lift adjustments both remain in history; the last event under that deterministic ordering wins.

Replay starts from immutable seeds, integrates automatic max events, then applies manual absolute values at their effective date (after automatic events on that same date). Later automatic events operate on the changed value. An absolute manual decision cancels already-pending temporary deload restores for that lift: the reviewed value becomes the baseline. Its generated Why records the cancelled restore count; original deload and manual audit events remain. Later relative increases and new deloads keep their normal behavior. Manual changes never rewrite the seed or count as an additional automatic bump. The progression preview keeps its historical log cutoff separately from the current prescription date, so a current-week manual change is visible. Session materialization re-evaluates adjusted percentage/RPE-load slots against the actual Start date, including early and overdue sessions, while calendar-week previews retain their scheduled dates. Legacy percentage slots use the dated event in the current profile unit. Active and completed rows are frozen copies and are not rewritten by a max edit. Active-entry diagnostic previews also exclude manual events recorded after that workout started and use its frozen session date; future-session previews use the latest effective event for their chosen date. The current programme detail and next-workout display use today's effective value, including an unknown pre-decision baseline.

Repeat opens a review sheet. It defaults to current effective values; the athlete may select saved increases or edit each final max. The guarded public action supplies `finishProgrammeBlock(..., {today, repeatMax: {values, unit}})`. Those are absolute final values: the core bypasses `definition.repeat.bump`, preventing a second bump. The new lap freezes the reviewed values as its new seed. The archived cycle keeps its seed, max cache and adjustment history. For compatibility, a direct caller omitting `repeatMax` retains the previous authored-bump and e1RM-rematerialization behavior. Week repeats retain their existing behavior and never add a block bump.

Reviewed Repeat values must remain finite and strictly positive after conversion into both profile-cache and definition-seed units. Underflow to zero or overflow refuses the transition without changing the document.

MCP `set_training_max` accepts `cycle_id`, `lift`, `value`, `unit`, optional `today` and `reason`, and required `expected_rev` plus `expected_wid`. **Preview is the default and sends no PUT**, including with the write gate off. The preview reports the current/proposed canonical max, effective date, unit, basis, audit event and training status. `apply:true` additionally requires the exact returned `preview_token` and `OPENGYM_ENABLE_PROGRAMME_WRITES=1`. Reuse the same reviewed input, including the effective date; read `get_programme` first to inspect basis, lift keys, seed/history and identity. Neither tool accepts transport flags, activity bodies or training-close proofs.

Previews live only in the MCP process, expire after 15 minutes, and bind the normalized action, authenticated API server/profile/configured credential, revision, write identity and canonical full client-visible document fingerprint. Apply reauthenticates `/api/me`, reads fresh `/api/data`, verifies that binding, and checks `/api/data/activity`. Only `idle` permits apply. A missing/invalid/unsupported guard endpoint fails closed; `active` and `unknown` refuse. It issues exactly one conditional PUT with `{state,baseRev,baseWid,stamped:true,requireIdle:true}` after normal `stampChange`; it never sends `active`, `trainingClose` or synthetic idle. There is no retry or rebase on 409 or 423 `TRAINING_NOW`. The preview token is consumed before the write attempt. API-token renewal retains the configured credential scope; changing configured credentials, server or profile invalidates the seal.

**Requires the reviewed W36 server training guard in the same release.** W29's earlier server does not provide trustworthy activity state, so this tool refuses it without PUT. The W36 server checks durable training metadata and revision/write identity atomically for agents, even if training starts after an idle preflight. Never infer idle from a server that strips `active` from its saved document. Phone-local sessions that never reached a heartbeat remain outside the guard's knowledge. This change does not retrofit the legacy activate/shift/skip surfaces.

After an exact acknowledgement/readback, a sealed `undo_token` is available for one hour when a positive previous max existed. `undo_training_max({undo_token,today?})` previews a **new compensating max decision**; applying it requires its own `preview_token`, `apply:true`, the same write gate, unchanged post-apply revision/write identity/full fingerprint and the exact original event. Its reason references the original decision id. It appends history and restores the prior absolute value at the reviewed date; it never deletes events, rewinds stamps, changes the original seed or rewrites logs. If no prior max existed, no safe compensating value can be inferred: undo is unavailable and the audit history remains. A changed document or target refuses compensation.

Invalid acknowledgements, changed readbacks and uncertain network writes never return replay or undo tokens. The tool attempts an immediate authenticated readback and reports the observed identity/event presence without claiming success. The next call is inspection-only against a fresh document; review that result and create a new preview. Process-local tickets are bounded to 32 entries/24 MiB and may be evicted; restarting MCP loses them. No server storage files are read or edited by these tools.

No live definitions are relabeled or converted by this feature. Repairing source bases and source-slot mappings is a separate, versioned library operation. No storage migration is required; older clients can round-trip the optional fields but cannot be relied on to evaluate them, so reload installed clients after deployment.
